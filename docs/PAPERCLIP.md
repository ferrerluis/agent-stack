# Paperclip in the optional workspace

## Initial experience

Set `workspace_paperclip_enabled = true` alongside `enabled_services = ["workspace"]`
(or include the other services you use). Supply the normal workspace SSH password
through your existing setup process; Paperclip requires no model API keys.
`variables.tf` owns the defaults: Paperclip `2026.1106.0` and Node.js `24.22.2`.
The code targets that upstream release; runtime qualification is a separate gate.
The bundled npm lockfile fixes transitive dependency versions and integrity
hashes; builds use `npm ci`. Updating the Paperclip release requires regenerating
this lockfile and rerunning runtime acceptance, not just changing a tag.

The workspace image gains Node/npm and the published `paperclipai` command. Codex,
Python, SSH, workspace UID/GID 1000, and the persisted home keep their existing
contracts. A Docker Compose companion named `paperclip` uses this same image and
home as the workspace user, starting after workspace SSH is healthy. Its process
can restart independently of SSH. It receives no workspace `.env`, model keys,
host credentials, Docker socket, or additional host mounts.

On the first start, the companion initializes embedded PostgreSQL and local disk
storage, generates three distinct internal signing secrets plus a local encryption
key, and seeds one `ACME Co` company with a `Codex` setup draft. Seeding uses a
temporary trusted API on **container loopback port 3101**, with the UI disabled.
This port is never published. The draft is created atomically with upstream's
`setupId` API, `status=paused`, `lifecycleState=paused`, and a `setup` hold. No active
agent is created and then paused. Heartbeat scheduling is explicitly disabled;
no issues, routines, paid calls, or live agent tasks are created.

The temporary process stops before the authenticated private server starts on
container port 3100. Docker publishes **only `127.0.0.1:3100` on the Docker host**.
The completed setup marker prevents future startup from entering trusted mode,
reseeding, restoring defaults, or unpausing agents. A lost company or agent create
response is recoverable using the saved company identity and deterministic setup
ID. Missing/corrupt markers, unexpected agents/runs, and existing unmanaged
Paperclip state cause a visible failure instead of data adoption or replacement.
`ACME Co` is only the initial display name. Repeated setup follows the saved
company ID and never resets a name that the user has customized. This change
does not migrate or rename existing real instances.

The first browser visit requires Paperclip sign-in and a first-owner claim. After
claiming ownership, the existing company and paused Codex draft are visible. This
is a human dashboard account, separate from a coding provider account. The
upstream claim URL is sensitive; it appears only in the private workspace file
`~/.paperclip/instances/default/logs/agent-stack-launch.log`, not Terraform
outputs or the general bootstrap log. Retrieve it through an already-authorized
workspace session. Claim links expire and are regenerated by upstream as needed.
No default human password or persistent board API token is invented.

## What the paused Codex draft means

The initial draft uses Paperclip's supported **legacy Codex CLI adapter**, with
`engine=cli`, so it can use the coding executable already supplied by the
workspace. `dangerouslyBypassApprovalsAndSandbox` is explicitly false. The newer
native Paperclip Runner is not silently substituted into this initial setup.
This feature does not configure additional coding harnesses or agents. The
published Paperclip package brings substantial adapter/runtime dependencies,
including code for other providers; their presence does not authenticate or
activate those providers.

An installed `codex` executable is not an authenticated Codex session. The draft
uses the separate, initially empty directory
`~/.paperclip/instances/default/codex-home`; it does not borrow `~/.codex/auth.json`
or import host/workspace provider credentials. Paperclip's own internal signing
keys are also not OpenAI keys. A setup-held draft cannot be resumed until its
setup is finished. Upstream also rejects run admission for paused agents.

The human must deliberately configure the provider/login, choose the model and
working project, finish the draft's setup, and explicitly activate it before real
work is allowed. Those steps can invoke upstream credential checks and must not
be automated as part of the initial seed. A zero monthly budget is **not** used
as the safety boundary: the setup hold, pause state, disabled schedule, empty auth
home, and lack of assigned work provide that boundary. If upstream changes this
behavior, runtime acceptance must fail rather than weakening the requirements.

## Access, persistence, and resources

No Tailscale Serve, Meshnet, bridge, routing, or firewall setting is changed by
this feature. For remote use, prefer an approved Tailscale HTTPS route to the
Docker host's loopback port. Preserve the existing OpenClaw Serve route; do not
run `tailscale serve reset` to add Paperclip. Add the approved hostname using
Paperclip's `allowed-hostname` command and configure its canonical auth URL when
needed. Applying mesh ingress is a separate action-time approval, not implied
by enabling the local companion.

With Docker inside a VM, that published loopback address belongs to the VM.
An agent using the physical host's browser can reach it through an approved SSH
forward, for example host `localhost:3100` to VM `127.0.0.1:3100`. The browser
still signs in to Paperclip. NAT supports this flow when VM SSH is reachable;
it does not require the guest to have its own LAN address. Other LAN clients
need their own approved tunnel or mesh route. This feature creates neither a
tunnel nor a shared browser session.

Compose gives the workspace, Paperclip, Hermes, and OpenClaw service-name DNS on
its default network. These are potential transport paths, not configured agent
integrations:

| Direction | Potential endpoint | Remaining application requirements |
| --- | --- | --- |
| Workspace or another container to Paperclip | `http://paperclip:3100` | New authenticated configurations allow `paperclip`; the workspace exports this API URL to container and SSH commands. A scoped CLI/API identity is still required. Existing saved Paperclip configurations are preserved and may need an approved hostname update. |
| Paperclip to OpenClaw | `ws://openclaw:18789` | Configure the upstream `openclaw_gateway` adapter, gateway authentication, device pairing, and a reachable callback URL. Agent Stack uses `OPENCLAW_GATEWAY_BIND=loopback` with Tailscale, so direct container access can be unavailable. |
| Paperclip to Hermes | Hermes API service, potentially `hermes:8642` | Enable a compatible API and configure `hermes_gateway` with its separate Hermes key. The adapter rejects non-loopback plain HTTP by default; choose an approved secure transport. |

Paperclip supports authenticated REST calls and board CLI tokens, plus scoped
agent API identities. Its experimental assistant MCP endpoint is disabled by
default and requires a deliberate feature enablement, reachable canonical
origin, and human OAuth consent. Agent API keys and MCP OAuth tokens are
different credentials. No Hermes/OpenClaw adapter, MCP client, API key, messaging
bridge, or common conversation/memory store is set up here. Browser/computer-use
tools available to a physical-host agent are not automatically available to
workspace or gateway agents.

NordVPN currently advertises Meshnet as supported. Its announced 2025 shutdown
was reversed; the December 3, 2025 macOS release notes explicitly state that
Meshnet remains live and supported. Meshnet's private-IP connectivity does not
automatically provide Tailscale Serve HTTPS. AgentStack's existing NordVPN egress
configuration is not a Meshnet deployment. This feature does not install or
configure a Meshnet client.

All Paperclip state is under the already-persisted workspace home:
`/opt/agent-stack/data/workspace/home/.paperclip`. Preserve the entire directory,
including database, uploads, configuration, encryption key, signing secrets,
bootstrap marker, and any later agent files. An SQL backup alone cannot restore
encrypted credentials or file assets. Disabling the feature stops/removes its
companion through the normal Compose lifecycle and retains the home data.
Database migrations can require a backup restore when downgrading; an image
rollback alone is not a database rollback.

The workspace image targets Linux **amd64 and arm64**. Paperclip's published
package, embedded PostgreSQL, Node, and Codex must actually start on each claimed
architecture; source inspection is not proof of runtime compatibility. A VM on a
Pi must use an ARM64 guest, while a typical x86 PC uses amd64. Docker and this
workspace run inside that VM and do not require container access to the personal
host's filesystem or its Docker socket.

Confirm the prepared guest's memory, available disk, OS and native architecture
before live qualification. Physical host RAM is not the guest's allocation.
No memory or latency target is claimed without measurements.

The user supplies a prepared Linux VM and a reachable address. Agent Stack
provisions only its guest runtime; it does not create the host VM, NAT, host
networking or tunnels. Native ARM64 and amd64 qualification remains required.

For a browser on the host, the user or their separately authorized agent can
create an SSH forward such as:

```sh
ssh -N -L 127.0.0.1:3100:127.0.0.1:3100 VM_USER@REACHABLE_VM
```

Use the VM's verified SSH host key and existing authorized identity. Then open
`http://localhost:3100` on that browser computer and sign in to Paperclip. If the
VM needs a jump host or mesh to be reachable, its owner establishes that path.
Agent Stack documents this operation but does not create or maintain the tunnel.

## Product acceptance catalog v4

All runtime cases require a disposable test instance with synthetic fixture
accounts, no provider credentials, no existing user auth, and no live agents.
Use the exact rendered image and record git revision, image digest, architecture,
Paperclip/Node/Codex versions, timestamp, commands, observations, and evidence
paths. Store JSON results and redacted evidence under `/tmp/agent-stack-tests`.
Missing Docker, another architecture, a browser, or authorized access is
**blocked**, never passed. Python fixture tests exercise our integration logic;
they do not qualify the actual upstream server or UI.

| ID | Prerequisites and repeatable steps | Expected result and evidence |
| --- | --- | --- |
| TC01.1 | Render the default workspace configuration with mocked Terraform; inspect Compose and image recipe. | Paperclip is absent, no Node/npm install is added, and existing services/SSH outputs retain their defaults. Save rendered artifacts and mocked assertions. |
| TC02.1 | Build the opt-in image; start a disposable workspace plus companion. Open the published loopback URL in a browser. Complete first-owner claim using a synthetic test account. | Login/claim UI works, then `ACME Co` and its `Codex` setup draft are visible. Save redacted screenshots, version/health output, and API observations. Never publish claim URLs or session cookies. |
| TC02.2 | With no session, request `/api/companies` and inspect Docker port bindings during and after first setup. | Protected API returns 401/403; port 3101 is never published; port 3100 is published only on host loopback. Preserve status codes and bindings. |
| TC03.1 | Read the starter agent via the authenticated API, repeat first setup using its deterministic setup ID, and list agents/runs. | Exactly one company and one paused setup-held Codex draft; scheduling disabled, sandbox bypass false, separate empty Codex home, no model credentials or runs. Preserve redacted agent configuration and counts. |
| TC03.2 | Try to resume or wake the incomplete paused draft using a synthetic human test session; wait through a scheduler interval. | Setup/paused admission is rejected and no coding process or model request starts. Preserve rejection response, run/process counters, and denied outbound-call evidence. |
| TC03.3 | Seed against the pinned server, which normalizes and redacts `CODEX_HOME` in its API response. Independently inspect only this fixture agent's stored home binding. | Setup completes with the redacted response, the stored home is the dedicated empty directory, and no secret-reveal request is made. Preserve the redacted response shape and the path-equality assertion. Regression B01. |
| TC04.1 | Restart and then recreate the companion using the same test volume. Repeat setup. | Company/agent identities, pause/setup hold, data, and internal key fingerprints persist; no duplicates, trusted-mode re-entry, unpause, or runs. Save before/after IDs, redacted state, and counters. |
| TC04.2 | Interrupt initialization after company creation and after agent creation in separate test volumes, then restart. Also try missing/corrupt markers and an unmanaged existing instance. | Lost-response retries create no duplicates; inconsistent or unmanaged data fails closed with no network-published trusted UI. Save crash/retry transcripts and counts. |
| TC04.3 | Start a fresh instance, verify its company is named `ACME Co`, deliberately rename that fixture company, then repeat setup and restart. | The initial generic name is correct, the saved company identity and custom name persist, and no duplicate company is created or real instance migrated. Preserve before/after IDs and names. |
| TC05.1 | Connect to the disposable workspace via SSH; run `codex --version` without reading/login/importing auth; exercise an existing Codex updater fixture and the default local suite. Restart only Paperclip. | SSH, Codex binary resolution, existing updater behavior, and existing mocked cloud-provider regressions remain functional. Paperclip restart leaves SSH available. Save commands and suite report. |
| TC05.2 | Exercise the prior-image rebuild fallback with an older workspace recipe and only its original files; separately remove a required Paperclip file from a new recipe. Use an isolated Docker-command fixture that checks the prepared build context. | The legacy path reaches Docker with its original context without requiring Paperclip files. A new recipe fails visibly before Docker when its required artifact is missing. Preserve shell-fixture results; actual image builds remain covered by TC06. Regression B03. |
| TC06.1 | On native Linux amd64, build and execute TC02–TC05 using the pinned release. | Server, embedded database, UI, and Codex executable behave as specified. Save native architecture, versions, image digest, and linked case results. |
| TC06.2 | Repeat TC06.1 on native Linux arm64 with suitable memory/storage. | Same required behavior, with independent ARM64 evidence. An amd64-only or emulated run does not count as native ARM64 qualification. |

Runtime product coverage is 6 parent cases / 13 sub-tests. V2 added TC03.3 for the
API redaction regression (10 to 11); v3 adds TC05.2 for legacy rollback (11 to 12).
V4 adds TC04.3 for the user's generic company-name and rename-preservation
requirement (12 to 13).
A parent passes only
when every required child has current evidence. Goal registration and planning
are workflow obligations, not product tests. Deployment to the personal device,
mesh access changes, and activating a real Codex agent remain outside these
credential-free tests and need their own authorization.
